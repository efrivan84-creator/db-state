# Права доступа

> [English](../../en/server/permissions.md) · **Русский**

Главное правило: доступ запрещён по умолчанию. Каждый RPC должен пройти read/write-решение на сервере.

## Deny-by-default

Если ни хук, ни `access` пользователя не разрешили действие, сервер вернёт `Read denied: <таблица>` или `Write denied: <таблица>`. Это касается и служебных таблиц `_user`, `_group`.

Порядок проверки:

```
1. Хук beforeRead / beforeWrite — может разрешить, запретить или промолчать
2. user.access                  — слит из групп при логине (эта страница)
3. Deny.
```

Первый шаг, вернувший явное решение, побеждает.

## Объект `access` на группе

Права — это **данные на группе** (`_group`):

```js
{
  _id: "montaj",
  name: "Монтажники",
  access: {
    zad:  { read: {}, write: { master: "$adminid" } },  // читает все заявки, правит свои
    bill: {
      read: { needact: true },                          // только совпавшие документы
      read_fields: ["fio", "balans"]                    // и только эти поля
    }
  }
}

{ _id: "boss", name: "Руководство", access: { fullaccess: 1 } }
```

Форма записи по таблице:

| Ключ | Значение |
|---|---|
| `read` | Фильтр строк для чтения. `{}` — все строки. Нет ключа — чтения нет. |
| `read_fields` | Белый список полей на чтение. Нет — все поля. |
| `write` | Фильтр строк для записи. `{}` — все строки. Нет ключа — записи нет. |
| `write_fields` | Белый список полей на запись. Нет — все поля. |

Единственный флаг — спецключ `fullaccess: 1` (доступ ко всему).

Значение `read` / `write` — **только объект-фильтр** (или массив фильтров как результат слияния групп). Любое другое значение правом не считается и означает полный запрет:

```js
{ zad: { read: {} } }              // доступ ко всем строкам
{ zad: { read: { city: "msk" } } } // доступ к совпавшим строкам
{ zad: { read: true } }            // ЗАПРЕТ — не фильтр
{ zad: { read: 1 } }               // ЗАПРЕТ — не фильтр
{ zad: { read: false } }           // ЗАПРЕТ
```

Так опечатка или старая запись в базе не превращается в неожиданный доступ.

## Слияние при логине

При логине сервер сливает `access` всех групп пользователя, затем личный `access` с документа `_user` поверх. Результат вешается на `user.access` и возвращается в `login_result` / `auth_result` — клиент может прятать разделы UI без лишних запросов.

Слияние только аддитивное, запретов нет:

- фильтры одного действия из разных групп складываются в **any-of** (документ подходит, если совпал хотя бы один);
- `{}` (все строки) шире любого фильтра;
- списки `*_fields` объединяются; право **без** ограничения полей снимает ограничение;
- сливаются **все** действия, а не только `read` и `write`: полномочия именованных методов (`bill: { pay: {} }`, `olt: { manage: {} }`) сливаются по тем же правилам и проверяются `accessAllows`.

Изменение `access` группы применяется при следующем логине или reconnect пользователя.

## Фильтры

Фильтр — обычный объект `dot.путь -> значение`, все пары должны совпасть (семантика Mongo). `{}` совпадает с любым документом.

Подстановки в значениях:

- `"$adminid"` — id текущего пользователя;
- `"$groupid"` — совпадение с любой из его групп (в запросе к базе превращается в `{ $in: группы }`).

```js
{ zad: { read: { master: "$adminid" } } }   // техник видит только свои заявки
{ zad: { read: { dep: "$groupid" } } }      // отдел видит свой участок
```

`write`-фильтр проверяется по **существующему** документу для `update` / `remove` и по **новому** — для `add`.

## Что покрывают `read` и `write`

| Действие | RPC-методы |
|---|---|
| `read` | `load`, `getIds`, `getUnique`, `count` и видимость изменений в `sync` |
| `write` | `add`, `update`, `remove` |

`read_fields` проецирует результат `load` и режет sync-изменения по полям. Если патч заменил родительский объект целиком (`set: { sip: {...} }`), а разрешены только вложенные поля (`sip.extension`), изменение разворачивается по ним: разрешённые значения уходят, остальное нет, а разрешённое поле, которого в новом объекте нет, у клиента удаляется. Если патч заменил родительский объект целиком (`set: { sip: {...} }`), а разрешены только вложенные поля (`sip.extension`), изменение разворачивается по ним: разрешённые значения уходят, остальное нет, а разрешённое поле, которого в новом объекте нет, у клиента удаляется. `write_fields` проверяет пути патча в `add` / `update` — патч, трогающий поле вне списка, **отклоняется целиком** с `Write denied: field <путь>` (ничего не вырезается молча).

Пустой список остаётся белым списком, а не отсутствием ограничения: `read_fields: []` отдаёт только всегда видимый `_id`, а `write_fields: []` запрещает все клиентские поля.

`read_fields` закрывает поле и для **фильтрации и сортировки**: запрос с условием или `getIds.sort` по скрытому полю отклоняется целиком с `Read denied: field <путь>`. Иначе значение подбиралось бы по наличию или порядку строк. Проверяются все обычные пути фильтра, включая вложенные в `$and` / `$or`, и полевой оператор роли не играет: `{ pass: "x" }` и `{ pass: { $regex: "^x" } }` отклоняются одинаково. Непрозрачные корневые операторы, зависимости которых нельзя безопасно определить (`$expr`, `$where`, `$text`, `$jsonSchema` и подобные), при активном `read_fields` отклоняются. `_id` разрешён всегда, поскольку всегда возвращается клиенту.

## Фильтры проверяет сама база

Проверки доступа уходят в Mongo, а не выполняются построчно в JS:

- `getIds` / `count` / `getUnique` добавляют условие права прямо в запрос (`{ $and: [фильтр_клиента, { $or: [фильтры_права] }] }`): база возвращает только разрешённые строки, `getIds` просит только `_id`, `count` считает через `countDocuments` без выгрузки;
- `load` проверяет фильтр одним `findOne({ $and: [{ _id }, фильтр] })`, а с `read_fields` просит у Mongo только разрешённые поля (projection);
- `sync` проверяет изменённый документ одним `findOne` сразу с фильтром права;
- `{}`-права и `fullaccess` решаются вообще без обращения к базе.

Это единственный путь чтения: построчной проверки больше нет, поэтому `skip` / `limit` всегда листают уже разрешённые строки.

Добавляйте обычные Mongo-индексы под поля фильтров прав (`master`, `dep`, ...) — условие права является частью запроса и выигрывает от индексов как любое другое.

## Именованные методы

Свои RPC-методы (см. README server-mongo) проверяют права сами:

```js
import { accessAllows } from "@db-state/server-mongo"

accessAllows(user.access, "bill", "write")            // есть ли доступ в принципе
accessAllows(user.access, "zad", "read", doc, user)   // доступ к конкретному документу
```

## Служебные таблицы

`_user` и `_group` подчиняются тем же правилам. Открывайте их в `tables` явно, когда админке нужно ими управлять, и выдавайте доступ как к любой таблице:

```js
{ _id: "admin", access: { _user: { read: {}, write: {} }, _group: { read: {}, write: {} } } }
```

Будьте осторожны с выдачей `write` на `_group` неадминским группам — они смогут расширить собственные права. Группы — обычная db-state таблица: админский UI может редактировать `access` на лету; для каждого пользователя изменения применяются при его следующем логине или reconnect.

## Когда фильтра мало

Если правило не выражается данными — внешние ACL, проверки по другим документам, свои проекции полей на роль — используйте [хук](hooks.md). `beforeRead` / `beforeWrite` решают первыми, могут переписать запрос, выставить `ctx.fields` и прямо разрешить или запретить.
