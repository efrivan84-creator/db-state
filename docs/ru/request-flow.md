# Карта прохода запроса

Как запрос клиента проходит через сервер: где стоят хуки, где проверяются права и где происходит обращение к базе.

Права как таковые живут в объекте `access` групп — см. [права доступа](server/permissions.md). Хук нужен там, где решение зависит от данных, которых в фильтре не выразить: см. [хуки сервера](server/hooks.md).

## Три этапа

Каждый запрос проходит одни и те же три этапа в фиксированном порядке:

```
1. хук before   — до обращения к базе
2. access       — права группы пользователя
3. хук after    — после обращения к базе
```

Имена хуков разные для чтения и записи, потому что это разные точки потока с разным составом данных:

| | Чтение | Запись |
| --- | --- | --- |
| До | `beforeRead` | `beforeWrite` |
| После | `afterRead` | `afterWrite` |
| При ошибке | `errorRead` | `errorWrite` |

Чтение — `getIds`, `load`, `count`, `getUnique`, `sync`. Запись — `add`, `update`, `remove`.

Главное различие между ними — **где внутри цепочки стоит сама база**.

---

## Чтение

```
запрос клиента
    │
    ├─ beforeRead ── false ──→ ЗАПРЕТ, причина клиенту
    │        │
    │        ├─ true ─────────→ права группы пропускаются
    │        └─ undefined ────→ проверяются права группы:
    │                                ├─ есть ли доступ к таблице
    │                                └─ read_fields  (по каким полям можно фильтровать)
    │                                       └─ нет права ──→ ЗАПРЕТ
    │
    ├─ ЗАПРОС В БАЗУ (фильтр клиента + фильтр права + проекция полей)
    │
    ├─ afterRead ─── false ──→ ЗАПРЕТ, причина клиенту
    │        │
    │        └─ иначе ────────→ ctx.result уходит клиенту
    │
    └─ ответ
```

`beforeRead` отрабатывает **до** запроса, поэтому может менять сам запрос — и права группы попадают в тот же запрос к базе. Недоступные строки не выбираются вообще, а не отсеиваются после выборки.

`read_fields` проверяется дважды, и по разным причинам: как проекция — чтобы скрытое поле не попало в ответ, и как список полей фильтра — чтобы по скрытому полю нельзя было искать. Без второй проверки значение подбирается перебором: поля в ответе нет, но по тому, вернулась строка или нет, видно, угадано ли оно.

`afterRead` стоит до отправки ответа, поэтому **может запретить**: ничего ещё не произошло.

## Запись

```
запрос клиента
    │
    ├─ beforeWrite ─ false ──→ ЗАПРЕТ, ничего не записано
    │        │
    │        ├─ true ─────────→ права группы пропускаются
    │        └─ undefined ────→ проверяются права группы:
    │                                ├─ фильтр строки  (можно ли трогать эту запись)
    │                                └─ write_fields   (можно ли трогать эти поля)
    │                                       └─ нет права ──→ ЗАПРЕТ
    │
    ├─ ЗАПИСЬ В БАЗУ  ← точка невозврата
    ├─ запись в журнал изменений
    ├─ рассылка сигнала другим клиентам
    │
    ├─ afterWrite ───────────→ может поправить ctx.result
    │
    └─ ответ
```

**`afterWrite` не может запретить операцию.** Он стоит после записи в базу, дозаписи журнала и рассылки — откатывать нечем, транзакций в библиотеке нет. Запрет на запись ставится только в `beforeWrite` или через права группы.

Это и есть причина, по которой `afterRead` и `afterWrite` называются по-разному: у них разные возможности, и одно имя вводило бы в заблуждение.

## Возврат хука

| Возврат | `beforeRead` / `beforeWrite` | `afterRead` | `afterWrite` |
| --- | --- | --- | --- |
| `false` или `{ allowed: false, reason }` | Запрет, цепочка прерывается, причина клиенту | Запрет | Игнорируется — запись уже произошла |
| `true` или `{ allowed: true }` | Разрешено, права группы **не проверяются** | Разрешено | — |
| `undefined` / `null` | Решения нет → проверяются права группы | Разрешено | — |

Правило: **явный запрет прерывает цепочку немедленно.** Всё остальное её продолжает.

`undefined` после запроса смысла не имеет — проверять уже нечего, поэтому в `afterRead` он равнозначен разрешению.

### Причина запрета

```js
beforeWrite: (ctx) => {
  if (ctx.method === "remove" && ctx.old?.locked) {
    return { allowed: false, reason: "Договор закрыт, удаление запрещено" }
  }
}
```

Клиент получит `dbstate:rpc_error` с этим текстом. Простой `false` без причины даёт общее сообщение вида `Read denied` / `Write denied`.

Запрет по правам группы причину не несёт — там лежат данные (`{ zad: { read: {} } }`), а не текст. Сообщение формируется автоматически: `Read denied: <таблица>`, а при отказе по полю — `Write denied: field <путь>`.

## Что хук может менять

Изменения `ctx` применяются всегда, независимо от того, что хук вернул. Можно вернуть `undefined` и при этом поправить запрос — тогда работа продолжится по правам группы, но уже с новым фильтром.

### `beforeRead`

| Поле | В каких методах | Что делает |
| --- | --- | --- |
| `ctx.filter` | `getIds`, `count`, `getUnique` | Уходит в запрос к базе |
| `ctx.sort`, `ctx.skip`, `ctx.limit` | `getIds` | Уходят в запрос |
| `ctx.fields` | `load`, `getIds`, `getUnique`, `sync` | Проекция: база вернёт только эти поля |

### `beforeWrite`

| Поле | В каких методах | Что делает |
| --- | --- | --- |
| `ctx.set`, `ctx.unset` | `update` | Что реально запишется |
| `ctx.obj` | `add` | Что реально вставится |

### `afterRead` и `afterWrite`

| Поле | Что делает |
| --- | --- |
| `ctx.result` | Итоговый ответ клиенту |

---

## Состав `ctx`

Общее для всех методов:

| Поле | Смысл |
| --- | --- |
| `method` | `load`, `getIds`, `getUnique`, `count`, `sync`, `add`, `update`, `remove` |
| `table` | Имя таблицы |
| `user` | Пользователь с полем `access` (слитые права групп) |
| `req` | Исходный RPC-запрос; `req.body` — payload клиента |
| `sessionId` | Сессия клиента |

Только при чтении: `filter`, `sort`, `skip`, `limit`, `field`, `id`, `obj`, `rows`, `result`.

Только при записи: `id`, `obj`, `old`, `set`, `unset`, `action`, `actorId`, `now`, `change`, `result`.

В `errorRead` / `errorWrite` приходит тот же `ctx` плюс `ctx.error`. Ошибка исходной операции остаётся главной: исключение внутри самого error-хука подавляется.

## Объявление хуков

Хук на каждое имя ровно один, общий на весь сервер. Таблица разбирается внутри него по `ctx.table`:

```js
hooks: {
  beforeRead: (ctx) => {
    if (ctx.table === "zad") { ... }
    if (ctx.table === "bill") { ... }
  },
  beforeWrite: (ctx) => { ... },
  afterRead: (ctx) => { ... },
  afterWrite: (ctx) => { ... },
  errorRead: (ctx) => { ... },
  errorWrite: (ctx) => { ... }
}
```

Вложенности по таблицам (`hooks: { zad: { beforeRead } }`) нет. Один хук — одна точка входа: не нужно помнить, какой из двух сработает первым и что будет, если первый запретил. Общие для всех таблиц проверки — санитизация фильтра, ограничение `limit` — пишутся без `if` и работают везде.

## Примеры

### Ограничить список своими записями

```js
hooks: {
  beforeRead: (ctx) => {
    if (ctx.table !== "zad" || ctx.method !== "getIds") return
    ctx.filter = { $and: [ctx.filter ?? {}, { ownerId: ctx.user._id }] }
    // возврата нет → дальше отработают права группы
  }
}
```

То же самое без кода — фильтром в правах группы:

```js
{ _id: "montaj", access: { zad: { read: { ownerId: "$adminid" } } } }
```

Предпочитайте второй вариант: он не требует кода и редактируется в интерфейсе.

### Санитизация запроса от клиента

```js
hooks: {
  beforeRead: (ctx) => {
    if (ctx.filter) ctx.filter = sanitizeFilter(ctx.filter)
    if (ctx.method === "getIds") ctx.limit = clampLimit(ctx.limit)
  }
}
```

### Скрыть поля по условию

```js
beforeRead: (ctx) => {
  if (ctx.method === "load" && !ctx.user.groups.includes("boss")) {
    ctx.fields = ["fio", "balans"]
  }
}
```

### Запретить с причиной

```js
beforeWrite: (ctx) => {
  if (ctx.method === "remove" && ctx.table === "bill") {
    return { allowed: false, reason: "Договоры не удаляются, используйте архив" }
  }
}
```

### Дополнить ответ

```js
afterRead: (ctx) => {
  if (ctx.method !== "load") return
  ctx.result = { ...ctx.result, canEdit: ctx.user.groups.includes("boss") }
}
```

### Аудит записи

```js
afterWrite: (ctx) => {
  audit.push({ who: ctx.actorId, what: ctx.method, table: ctx.table, change: ctx.change })
}
```

## Что где решать

| Задача | Где |
| --- | --- |
| «свои документы», «только своя группа», «только активные» | Фильтр в правах группы (`$adminid`, `$groupid`) |
| Постоянный список видимых полей для роли | `read_fields` в правах группы |
| Условие зависит от времени, параметров запроса, другой таблицы | `beforeRead` / `beforeWrite` |
| Жёсткий запрет с понятным текстом | `beforeRead` / `beforeWrite` |
| Обогатить или переформатировать ответ | `afterRead` |
| Аудит и метрики | `afterWrite`, `afterRead` |

Правила, которые выражаются фильтром, лучше держать в правах группы: они уходят прямо в запрос к базе, редактируются администратором и не требуют перезапуска.
