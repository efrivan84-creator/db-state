# Changelog

Описание изменений и статус проекта db-state.

## Unreleased

## 0.3.6

- Новый файловый хук `readChange`: вызывается при `sync` на каждое изменение, с `table`, `id`, `change` и `loadDoc()`. Правило строки, которое фильтром права не выразить, — членство в другой коллекции, право на родительский документ, — до сих пор нельзя было применить к синхронизации: у внешнего хука `sync` нет `table`, изменения проверялись только фильтрами группы, и `fullaccess` получал всё. Приложениям приходилось повторять правило в общем `afterRead`, разбирая `ctx.result.changes` вручную, и забытая таблица означала утечку через sync при правильных списках. `false` не отдаёт изменение, `true` отдаёт без права группы, отсутствие решения оставляет право группы; `ctx.fields` урезает поля и пересекается с `read_fields`. Хук опциональный: без файла `sync` работает как раньше. Табличный `beforeRead` на изменения по-прежнему не вызывается — он сужает фильтр и разрешает запрос, а у изменения фильтра нет, и его «разрешено» открыло бы таблицу.

- Документация и demo. README описывает, чем db-state отличается от Meteor, Hasura, Firebase/Supabase, Convex и local-first синхронизации, для чего подходит лучше всего и где её граница. `demo/` показывает `readChange` (заметки к заказам: видит тот, кто может править заказ) и слияние полномочий (`order.number` из отдельной группы, пользователь `viewer`); `demo:smoke` проверяет это через WebSocket и теперь входит в `npm test`. In-memory Mongo в demo понимает `$and`/`$or`/`$in`, которые библиотека строит сама, накладывая права. `@db-state/core` и `@db-state/vue` выходят с той же версией без изменений в коде.

- Слияние прав при логине сохраняет **все** действия, а не только `read` и `write`. Полномочия именованных методов (`bill: { pay: {} }`, `olt: { manage: {} }`) записывались в группе, но при входе молча пропадали, и `accessAllows(user.access, "bill", "pay")` отвечал «нет» тому, у кого право есть; заметно это было только не у `fullaccess`. Теперь действия берутся из самих данных и сливаются по тем же правилам: фильтры — any-of, `{}` шире любого, `<действие>_fields` объединяются.

## 0.3.5

- Массив значений в фильтре права теперь и в запросе к Mongo означает «совпадает любое». Раньше два пути одного и того же права расходились: проверка уже прочитанного документа принимала `{ city: ["msk", "spb"] }` как «любой из городов», а в запрос массив уходил как есть — то есть «поле равно этому массиву», — и чтение по фильтру молча отдавало пусто. Заметить это тем труднее, что подстановка `$groupid` в `$in` превращалась правильно, и правило с ней работало, а точно такое же правило со списком значений — нет. Форма записи прав в документации не менялась (docs: access), исправлено только её исполнение.

- Файловые RPC-методы в подпапке `pub/` вызываются без авторизации: `rpc/pub/auth/register.js` становится методом `"pub.auth.register"`. Регистрация и восстановление пароля иначе не выражаются — чтобы позвать обычный метод, нужна сессия, а это ровно то, чего у человека ещё нет; до сих пор такие сценарии приходилось делать модулем `files`, перехватывая сообщения до библиотеки. Признак — папка, а не список в конфиге и не префикс в имени файла: «что открыто наружу» видно командой `ls rpc/pub`, файл либо лежит в папке, либо нет, и опечатке негде спрятаться. Имя метода у клиента несёт ту же метку, поэтому открытый вызов виден в браузере и в логах. Публичный метод не получает `user` и проверяет вход сам — ограничение попыток и одноразовые коды остаются на приложении. Табличные команды (`load`, `getIds`, `update`, `sync`) публичными не становятся никогда, а без `methodsDir` публичных методов нет вовсе: вызов `pub.*` на таком сервере по-прежнему отклоняется как `Unauthorized`, а не как неизвестный метод — иначе разный ответ на существующий и несуществующий метод позволял бы их перебрать.

## 0.3.4

- Опция `serverInfo` у `createDbStateServer` уезжает клиенту в сообщении `hello`, а Vue-клиент показывает её как `state.sync.server`. `hello` — единственное сообщение, которое клиент получает до авторизации, поэтому страница входа может показать, с какой сборкой говорит — ветку, коммит, дату деплоя — без отдельного эндпоинта. RPC для этого не годится: до авторизации он отклоняется. Без `serverInfo` сообщение `hello` остаётся байт в байт прежним, а голое `hello` от старого сервера сбрасывает `state.sync.server` в `null`, не оставляя на экране данные прошлого подключения.

## 0.3.3

- Хуки теперь получают всё, что передано через `methodsContext`, — те же дополнительные зависимости, которые уже получали файловые методы: вторую базу, исполнитель транзакций, внешний клиент. То, что нужно методу, нужно и хуку, реагирующему на запись; прежнее разделение делало операцию доступной из метода, но недоступной из соответствующего хука. В `ctx` хуков поля `db` и `api` принадлежат серверу и не перекрываются одноимёнными ключами. Файловые методы сохраняют прежнюю семантику слияния, где `methodsContext` может переопределить их значения по умолчанию; защита относится именно к `ctx` хуков.

## 0.3.2

- `api.notifyChanges()` рассылает тот же сигнал `changes_available`, что и обычная запись, но сам ничего не пишет. Это нужно коду, который фиксирует несколько документов транзакцией через сырой драйвер: строки журнала создаются через `createChange` из `@db-state/core` и записываются в той же транзакции, а `notifyChanges` вызывается только после успешного commit. Вызов внутри транзакции преждевременно разбудил бы клиентов, а журнал вне транзакции мог бы пережить её откат. Транзакции требуют replica set; standalone MongoDB их не поддерживает.

## 0.3.1

- Хуки теперь получают в `ctx` поля `db` и `api` — ту же пару, которая уже была у файловых методов. Раньше хук мог решить судьбу запроса, но для реакции на запись приходилось отдельно импортировать Mongo, а серверный API был недоступен. `db` — драйвер как есть, без прав, журнала и рассылки; `api` выполняет те же команды, что клиент, с обычными правами, журналом и `changes_available`. Контекст добавляется централизованно перед цепочкой хуков; `api` собирается в конце `createDbStateServer`, но прикрепляется до возврата фабрики, поэтому доступен уже на первом запросе. Значения, подставленные модульным хуком, видны следующим файловым хукам.
- Запись через `ctx.api` из `afterWrite` снова входит в тот же хук. Встроенной защиты от рекурсии нет: передавайте в `req` собственную метку (`{ ...ctx.req, internal: true }`) и выходите из хука, когда она присутствует. `req` доходит до вложенного вызова без изменений.
- Декларации типов теперь корректно разрешаются в ESM с `moduleResolution: NodeNext`: относительные импорты содержат `.js`, `ServerHookContext` объявляет `db` / `api`, а модуль `@db-state/server-files` больше не заявляет удалённое конфигурационное поле `access`, которого нет в runtime.

## 0.3.0

- **Ломающее изменение: хуки и именованные RPC-методы объявляются только файлами.** Объектов `hooks` и `methods` в конфиге больше нет — `createDbStateServer` падает с `"hooks" is removed, use "hooksDir"` (и так же для `methods`), а не игнорирует их молча: иначе защита, написанная в конфиге, тихо перестала бы работать. В `hooksDir` файл `<dir>/beforeRead.js` действует на все таблицы, `<dir>/order/beforeRead.js` — только на свою; общий выполняется первым, первое явное решение останавливает цепочку. Хуки модулей — отдельный слой и по-прежнему идут перед обоими: они часть модуля (так `@db-state/server-files` защищает свою таблицу), а не конфигурации приложения.
- Файлы хуков и методов сверяются с mtime **не чаще раза в минуту**, а не при каждом вызове. И то, и другое вызывается на каждой операции, поэтому `stat` перед вызовом был самой дорогой частью простого хука. Правка применяется в пределах минуты; интервал задаётся опцией `reloadCheckMs`, значение `0` возвращает проверку на каждый вызов — удобно при разработке.
- `hooksDir` теперь работает fail-closed: если явно заданную папку или ещё не загруженный файл хука нельзя прочитать, операция завершается ошибкой, а не продолжает работу без хуков приложения. Если уже загруженный файл исчез или временно недоступен, до перезапуска остаётся активной его последняя рабочая версия. Подпапки таблиц поддерживают служебные имена с начальным `_`, включая `_user` и `_group`.

## 0.2.0

- **Ломающее изменение: `change.logId` переименован в `change._id`.** Запись журнала несла одно значение дважды — `logId` в полезной нагрузке и `_id` как ключ Mongo, — потому что протокольное поле и ключ хранилища держали раздельно. Расходиться им было не с чего, поэтому дубль убран: идентификатор изменения — это `_id` самой записи журнала. Поправьте код, который читает `change.logId` из `sync`, и пересоздайте индекс журнала как `{ createdAt: 1, _id: 1 }` (старый `{ createdAt: 1, logId: 1 }` больше не соответствует сортировке). `createLogId` сохраняет имя и роль — он генерирует это значение.
- Существующие записи журнала до 0.2 остаются читаемыми: `sync` нормализует их в новую публичную форму, убирая legacy `logId`, пустые payload-поля и неизвестные внутренние поля.
- `info.editid` / `info.editdata` больше не пишутся в `change.set` при обновлении. Они повторяли то, что запись журнала уже сообщает через `userId` и `createdAt`, а клиент применял их к своему кэшу при каждой синхронизации. В документах `info` остаётся — там оно читается вместе с записью; дублировать его перестал только журнал. Поэтому уже загруженная на клиенте запись больше не обновляет эти два поля `info` через update-change; если UI их показывает, документ нужно перечитать. `insert` и `delete` не затронуты: их `obj` / `old` — полные снимки документа, где `info` является частью документа, а не повторённым полем журнала.
- Записи журнала больше не хранят `null` в полях, которые действие не использует. Раньше запись собиралась поверх явного `_id` при вставке, из-за чего материализовались все отсутствующие поля: обычный `update` писал `unset`, `obj`, `old` и `sessionId` как `null` рядом с единственным изменившимся полем.

## 0.1.4

- **Безопасность: `read_fields` теперь ограничивает и фильтр.** Запрос с условием по скрытому полю раньше выполнялся как обычно: поле не попадало в ответ, но по наличию строк в результате было видно, угадано ли значение, — то есть его можно было подобрать перебором. `read_fields` защищал вывод, но не запрос. Теперь пути фильтра проверяются тем же белым списком, и чтение отклоняется с `Read denied: field <путь>`. Пути внутри `$and` / `$or` проверяются тоже, оператор роли не играет. `getUnique` так проверял свой аргумент `field` и раньше; сам фильтр не проверялся нигде.
- То же правило действует на `getIds.sort`, потому что порядок строк тоже раскрывает скрытые значения. Непрозрачные корневые операторы, зависимости которых нельзя безопасно определить (`$expr`, `$where`, `$text`, `$jsonSchema` и подобные), при активном `read_fields` отклоняются. `_id` остаётся доступен, поскольку всегда возвращается клиенту.
- Пустой белый список больше не считается отсутствием ограничения: `read_fields: []` отдаёт только всегда видимый `_id`, а `write_fields: []` запрещает все клиентские поля.

## 0.1.3

- **Ломающее изменение: сохранённый вход хранится одним JSON-объектом.** Вместо `userIdKey` и `authHashKey` — один ключ `authKey` (по умолчанию `"db-state.auth"`) со значением `{ userId, hash }`. Хранилища умеют только строки, поэтому плоское значение теряло тип: при `numericIds` числовой `_id` возвращался как `"1"`, `authByHash()` спрашивал у сервера `_id: "1"`, получал `Unauthorized` и стирал сохранённые данные — «запомнить вход» молча переставал работать без возможности повторить попытку. JSON сохраняет тип, а запись пары одним значением заодно исключает состояние «id есть, хеша нет». Испорченное или чужое значение считается отсутствием входа. Старый формат из двух ключей не читается: кто был авторизован до обновления, войдёт один раз заново.

## 0.1.2

- Исправлено: при `numericIds` Vue-клиент не мог загрузить документ через `load()`. Клиент приводит id к строке для своих ключей — реактивной таблицы, кэша, отметок загрузки, — но ту же строку отправлял на сервер, а Mongo не сопоставляет `"1"` с `_id: 1`, поэтому чтение молча возвращало пустоту. Теперь строка используется только как ключ, а на сервер и в само поле `_id` документа уходит исходное значение. То же исправление в `__retryUnloaded` и `resetRecord`: они восстанавливали id из ключа объекта (всегда строка) и теряли тип при переподключении и смене пользователя.

## 0.1.1

- `createDbStateServer({ numericIds })` назначает новым документам последовательные целочисленные `_id` — 1, 2, 3 — вместо uuid. Значение `true` включает нумерацию для всех таблиц, массив (`["order", "bill"]`) — только для перечисленных; по умолчанию остаётся `false`, поэтому без явного включения поведение не меняется. Номера выдаёт коллекция счётчиков (`_counter`, один документ на таблицу; имя меняется через `counterCollection` и получает тот же service prefix) атомарной операцией `$inc`, поэтому параллельные процессы не получают одинаковый номер. Переданный клиентом `_id` используется как есть и не расходует номер. Пропуски допустимы: номер выделяется до вставки, поэтому неудачная или удалённая запись оставляет разрыв. При ручном заполнении базы нужно заполнить и счётчик.

## 0.1.0

- **Ломающее изменение sync:** `syncLimit` и клиентский лимит числа changes удалены. Один ответ сервера покрывает не более 12 часов, `hasMore` заставляет Vue-клиент последовательно догнать все окна, а cursor старше 20 дней получает `reset: true`, после чего клиент очищает cache и перечитывает текущее состояние.
- `state.auth` теперь хранит, кто вошёл: поля `login`, `groups` и `access` заполняются из ответа сервера при `login()` / `authByHash()` и очищаются при выходе или отклонённом hash. В `login_result` / `auth_result` добавлен `login` пользователя, поэтому приложение может показать текущего пользователя без отдельного запроса.
- `applyChange` в `@db-state/core` создаёт записи с ключом `_id`, а не `id`: `insert` без `obj` и `update` по неизвестной записи раньше давали документ, нарушающий `BaseDoc`.
- `add` принимает устаревший `id` как ключ документа, но больше не сохраняет его рядом с `_id`.
- В `login_result` / `auth_result` приходит то поле, по которому пользователь реально вошёл: при `authLoginFields: ["login", "email"]` пользователь только с `email` получает `login: "ivan@example.com"`, а не пустое значение.
- **Ломающее изменение: реактивные документы больше не дублируют `_id` в `id`.** Каждая запись несла одно и то же значение дважды; ключ теперь только `_id` — как в Mongo и в журнале изменений. В шаблонах замените `row.id` на `row._id` (`:key`, выбор строки). Поле `id`, переданное в `add()`, по-прежнему принимается как ключ документа, а `change.id` и `UpdateArgs.id` не менялись — правка касается только самих объектов документов.
- **Ломающее изменение: code-правила доступа удалены.** Опции `createDbStateServer({ access })` больше нет — права живут только в объекте `access` групп пользователя, а динамические решения переехали в хуки. Хук `beforeRead`/`beforeWrite` теперь может вернуть `false` или `{ allowed: false, reason }` для запрета (причина уходит клиенту), `true` — разрешить и пропустить проверку группы, либо ничего — тогда решает `access` группы; правки `ctx` применяются в любом случае. `beforeRead` может выставить `ctx.fields` и сузить набор возвращаемых полей (расширить разрешённое `read_fields` нельзя). Раз code-правил нет, исчез и построчный fallback в `getIds`/`count`/`getUnique`: фильтр права всегда уходит в Mongo-запрос, поэтому `skip`/`limit` всегда листают уже разрешённые строки. Вместе с этим удалены `AccessConfig`, `AccessRule`, `canAccess` и `filterReadable`.
- **Ломающее изменение: хуки объявляются один раз на имя для всего сервера.** Вложенности по таблицам (`hooks: { order: { beforeRead } }`) больше нет — таблица разбирается внутри хука по `ctx.table`. Хуки подключённых модулей теперь выполняются перед хуком приложения с тем же именем, а не затирают его; первое явное решение останавливает цепочку.
- `errorRead` / `errorWrite` теперь срабатывают и когда запрошенной таблицы нет в `tables`: раньше ошибка бросалась до того, как хук мог её увидеть.
- Сообщения `Read denied` / `Write denied` теперь называют таблицу.
- `@db-state/server-files` больше не поставляет code-правила: таблица файлов защищена собственными хуками, `storageKey` не покидает сервер ни при каком чтении через CRUD, а права на метаданные настраиваются обычным `access` группы. Попутно исправлена ошибка: завершение загрузки читало файл обратно без внутренней пометки.
- **Ломающее изменение: `meta.accessFiltered` и `meta.denied` удалены.** Сколько строк или изменений скрыли права чтения, больше не сообщается — клиенту это не нужно, а число недоступных строк само по себе утечка. Сервер их больше и не считает, поэтому из `getUnique`/`sync`/`count` ушёл построчный подсчёт. `meta.fieldsFiltered` остался: он выводится из уже разрешённого права без дополнительной работы. Теперь в `meta` попадает только то, что серверу известно и так, — ради него ничего не считается и не перезапрашивается. Вместе с этим удалены `hasHiddenFields` и `hasHiddenChangeFields`.
- Значение `read`/`write` должно быть объектом-фильтром (или массивом фильтров как результатом слияния групп). Любое другое значение — `true`, `1`, `false`, `""`, `[]` — правом не считается и означает запрет, поэтому опечатка или старая запись в базе не могут молча расширить доступ. `accessAllows` работает по тому же правилу.
- Пользователь разрешается один раз на запрос, а не отдельно в `userReadPlan` и по разу на строку — снят N+1 для собственных реализаций `getUser`.
- Значение `read`/`write` — всегда фильтр по документу: `{}` = все строки (полный доступ к действию), `{ enable: true }` = только совпавшие; после слияния групп — any-of массив. `read_fields`/`write_fields` — белые списки полей. Единственный флаг — спецключ `fullaccess: 1`. Подстановки в фильтрах: `"$adminid"` (id пользователя) и `"$groupid"` (любая из его групп) — «свои документы» вообще без кода. `write`-фильтр проверяется по существующему документу для `update`/`remove` и по новому для `add`; sync лениво догружает документ только при фильтре. Фильтры проверяет сама база одним запросом: списки и `count` получают условие права прямо в Mongo-запрос (`count` — через `countDocuments`, без выгрузки строк), `sync` и `load` делают `findOne` сразу с фильтром, `load` с `read_fields` получает от Mongo только разрешённые поля (projection), `getIds` — только `_id`, `"$groupid"` в запросе превращается в `{ $in: группы }`. `accessAllows` принимает необязательные `doc`/`user`, добавлен экспорт `matchesAccessFilter`.
- **Ломающее изменение: таблица `_permission` удалена.** Права теперь — объект `access` на группе (`_group`): `{ zad: { read: {}, write: {} }, bill: { read: { needact: true } }, fullaccess: 1 }`. При логине сервер аддитивно сливает `access` всех групп пользователя (плюс личный `access` на `_user`), вешает его на `user.access` и возвращает в `login_result`/`auth_result`. Порядок проверки: хук `beforeRead`/`beforeWrite` → `user.access` → deny. Декларативные фильтры `read`/`write` ограничивают строки, а `read_fields`/`write_fields` — поля; хуки остаются для динамических, внешних и междокументных решений. `read` покрывает `load/getIds/getUnique/count` и видимость `sync`; `write` — `add/update/remove`. Новые экспорты: `accessAllows(access, table, action)`, `matchesAccessFilter` и `mergeUserAccess`. Заодно исчез N+1 запрос к `_permission` в `getIds`/`count` и кэш правил в `sync`.
- `@db-state/server-mongo`: `createDbStateServer({ methods })` регистрирует свои именованные RPC-методы в том же WebSocket-роутере, что и встроенные CRUD/sync; модули (`files`) могут добавлять методы через поле `methods`, как `hooks`; коллизия со встроенным именем — ошибка при старте. Встроенные проверки доступа и лог изменений применяются только к стандартным CRUD — именованный метод, пишущий в базу напрямую, сам отвечает за права и аудит.
- `@db-state/server-mongo`: `createDbStateServer({ methodsDir, methodsContext })` — методы-файлы: `"zad.get-num"` соответствует `<папка>/zad/get-num.js` (export default = обработчик). Файл читается лениво при первом вызове и перечитывается при изменении mtime — правки применяются без перезапуска; сегменты имени валидируются, так что имя от клиента не может выйти за пределы папки; встроенные методы и `methods` имеют приоритет. Каждый файловый метод по умолчанию получает `db` и `api`; `methodsContext` добавляет своё поверх и может их переопределить. `handleRpc` принимает необязательный резолвер четвёртым аргументом.

## Текущие ограничения

- Переносимый контракт декларативных фильтров `access` — equality-style matching с dot-path полями и подстановками `"$adminid"` / `"$groupid"`. Для динамических, внешних и междокументных условий используй хук `beforeRead`.
- Мультидокументные записи пока не атомарны. Для сценариев, где нужно менять несколько таблиц вместе, используй application/server-side код; `batch()`/transaction API планируется.
- Именованные и файловые методы являются first-class RPC, но прямые записи в базу внутри них автоматически не проходят встроенные проверки доступа и не добавляются в db-state change log.
- File transfer v1 не умеет resumable upload после reconnect; прерванный upload получает `failed`, а временный файл удаляется.
- Встроенный file storage adapter - local filesystem. Для S3-compatible/object storage нужен custom `FileStorage` adapter.
- File module сейчас разрешает один active upload и один active download на socket, чтобы backpressure оставался простым.
- Wake-up сигналы изменений уже идут через debounce/rate-limit, но для больших инсталляций может понадобиться per-table/per-client filtering или custom broadcast layer.
- Sync обрабатывает все строки в окнах не более 12 часов. Cursor старше 20 дней запускает очистку клиентского cache и перечитывание текущего состояния.
- Offline writes намеренно не ставятся в очередь. Клиент поддерживает offline read, а записи требуют онлайн-сокет.
- React, Postgres, SQLite и другие адаптеры не входят в текущий пакет.
